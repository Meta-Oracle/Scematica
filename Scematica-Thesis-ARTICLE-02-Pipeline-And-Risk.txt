Part Three: The Sniper Pipeline, Stage by Stage

The sniper is the heart of Scematica, and it is best understood as a pipeline that a candidate token flows through.

The first stage is the listener layer. Several sources of new-pool events, a Raydium AMM V4 listener, a Pump.fun source, and a whale-copy source, all merge into a single unified event stream. Everything downstream is deliberately blind to where an event came from, which means new sources can be added without touching the rest of the pipeline. This is a recurring architectural theme in Scematica: define one clean seam, then let many implementations plug into it.

The second stage is the filter pipeline. Each filter is a small, independent unit that answers one yes-or-no question about a candidate pool: Is the mint authority renounced? Is the liquidity provider token burned? Is the pool large enough, but not so large it is already an established, post-pump token? Does the deployer have a history of rug pulls? Does the pool pass a predictive quality score? Filters run with a hard per-call timeout, three seconds, and they are designed to fail open rather than stall the whole queue when a single RPC node is slow. This matters enormously in practice, because the alternative, a pipeline that freezes when one network call hangs, forfeits the speed that is the entire point.

The third stage is the executor. Once a token passes the filters, the executor builds the actual swap transaction. It handles the lifecycle of the wrapped-SOL associated token account, constructs the Raydium swap instruction, and escalates the priority fee dynamically so the transaction lands even when the network is congested. Getting this layer right is the difference between a bot that decides to buy and a bot that actually buys.

The fourth stage is the sniper main loop, which orchestrates the whole thing: buy, then monitor the position, then exit. The sell monitor deserves special attention because it is where a great deal of the profit and pain lives. It runs in two phases. For the first twenty checks it polls the price every hundred milliseconds, watching for a rapid post-buy dump; a detector that fires on three consecutive declines catches the tokens that pump for a heartbeat and then collapse. After that initial burst it settles into a slower cadence. Crucially, it re-reads its take-profit and stop-loss parameters on every single iteration, which is what allows the operator to change strategy live, from the dashboard or the mobile app, without restarting anything.

A subtle but important design choice runs through all of this: configuration uses defaulted fields everywhere, so that adding a new setting never breaks an existing configuration file. The bot has evolved through many versions and dozens of new parameters, and an operator's old config keeps loading the whole way through.

Part Four: The Risk Subsystems

A trading bot without brakes is a way to lose money quickly. Scematica has a family of independent circuit breakers, each living in its own module, each able to pause buying on its own, and each following the same pattern so new ones can be added consistently.

There is an all-time-high tracker that pauses buying when the wallet draws down a configured percentage below its session high, so a good run cannot fully unwind. There is a grief breaker that watches cumulative loss inside a five-minute sliding window and halts if losses come too fast, which protects against a bad market regime or a spate of rugs. There is a fractional-Kelly position sizer that adjusts entry size from a rolling win rate, betting more when the edge is present and less when it is not. There is a pool scorer that turns a pool's age and liquidity into a predictive quality number and rejects anything below a threshold. There is a deployer-reputation ledger that blends each deployer's rug history into a moving average and rejects serial ruggers. And there is a multi-RPC failover that ranks endpoints by latency and rotates across them, because in this game a slow node is a lost opportunity.

The philosophy behind all of these is defensive asymmetry. The bot is designed to lose small and often, and to win big and rarely. The breakers exist to guarantee the "small" in "lose small." As the data will show, this asymmetry is not incidental. It is the entire source of profitability.
