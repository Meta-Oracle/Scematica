Part Five: The Deep Q-Star Agent

The most ambitious intelligence layer in Scematica is a reinforcement-learning agent written from scratch in pure Rust, with no external machine-learning framework. This was a deliberate choice: the agent lives inside the sniper process, must be fast, and must not drag in a heavy dependency tree. Everything, the neural network, the training loop, the replay memory, is hand-built.

The agent is a Double, Dueling Deep Q-Network. Its input is a twenty-four-dimensional description of the current trading situation, normalized to a common range: the pool's age and liquidity, recent price change and volume, the buy-to-sell ratio, whether liquidity is burned and mint authority renounced, the current profit-and-loss and position age, daily profit, win and loss streaks, wallet balance, market regime, volatility, spread, time of day, the number of open positions, and several velocity and acceleration signals that capture the shape of the price move. From that state the agent chooses among five actions: hold, buy at standard size, buy aggressively, sell part of the position, or sell all of it.

The training machinery is genuinely sophisticated for a hand-rolled implementation. It uses Double Q-learning, where one network selects the best action and a separate target network evaluates it, which reduces the well-known tendency of Q-learning to overestimate. It uses prioritized experience replay backed by a sum-tree, so the agent learns more from surprising transitions than from routine ones. It uses multi-step returns to propagate reward faster. It branches into separate network pairs per market regime once it has trained enough, so that "what to do in a bull regime" and "what to do in a panic regime" are learned separately. And it runs a small tournament of three parameter variants in parallel, promoting whichever is performing best.

The way the agent influences live trading is careful and conservative, and this care is itself a lesson. The agent does not get to trade freely from day one. It must first accumulate enough training steps and produce a signal with enough confidence. Only then does it begin to size entries, buying larger when it is bullish and smaller when it is unsure, and to veto a buy when it is strongly bearish. Even the veto is bounded: a weak bearish lean only downgrades the position size, and only a strong bearish signal fully suppresses a buy. This design exists precisely so that a half-trained network cannot silently switch off a proven, profitable strategy. It is a template for how to add a learning component to a system that already makes money: let it advise, then let it size, and only let it veto once it has earned the right.

Later work extended the agent with optional, opt-in modules: a distributional value head that models the full distribution of returns rather than just the average, a Dreamer-style latent world model that learns to imagine future states, and an adversarial pool simulator that trains the agent against a synthetic environment designed to fool it. These are research-grade additions, gated behind feature flags, that push the agent toward robustness.

Part Six: The Evolution of the Exit Strategy

If there is one part of Scematica that has been revised more than any other, it is the exit logic, the question of when to sell. This is not surprising. Entering a memecoin is a single decision; exiting one is a running battle against a price that can 10x or evaporate in seconds. The history of the exit strategy is a history of hard-won lessons, and it is worth recounting because it shows the project learning from its own mistakes.

Early versions suffered from a stale-target bug that quietly killed the escalation logic: the take-profit target was not being refreshed correctly, so a position that should have been allowed to ride a runner instead exited early. There was a velocity-window bug that mis-measured how fast the price was moving. There was a period where profit-and-loss was computed from an estimate rather than the actual swap output, which made the exit decisions subtly wrong. There was even a spectacular class of bug where a position would report a 99-percent profit that did not exist, traced back to how the momentum window re-armed at the 100-percent mark.

Each of these was found by staring at the real trade log, forming a hypothesis, and fixing the specific mechanism. Out of that process came the current exit architecture: a tiered partial-take-profit ladder that sells a slice of the position at each of several gain levels and, after the first tier fires, moves the stop to break-even so the trade can no longer become a loss; a profit-lock that permanently raises the stop toward break-even after the position holds above entry for several consecutive checks; a momentum escalator that raises the take-profit target as long as genuine velocity persists, so a real runner is allowed to run; a velocity-decay exit that bails when the price stops advancing; and a peak-stagnation exit that closes a position that has escalated but then stalled.

There is a mathematical invariant buried in this logic that the project had to learn the hard way, and it is worth stating because it captures the flavor of the whole exit problem: the peak that arms the pullback exit must exceed the sum of the initial take-profit and the pullback percentage, or the exit condition can never be satisfied and the position rides all the way down. Getting these thresholds to be mutually consistent, rather than each individually reasonable but collectively unsatisfiable, is most of the art.

Part Seven: The Recurring Failure Mode

Any honest thesis about Scematica must describe its most persistent failure, because understanding it is the key to operating the bot well.

Repeatedly, across many sessions, the bot has been broken in the same way. Someone, reacting to a run of losses, makes the filters stricter, demanding only the highest-quality, highest-scoring pools. The intuition is obvious: buy only the best. But the result is perverse. Because the sniper structurally arrives after a token's initial pump, the only pools that can pass a very high quality bar at the moment of detection are the ones that are still visibly ripping upward, which is to say the ones that are already parabolic and about to reverse. The bot buys the top. Then the momentum escalator, seeing a fast-moving price, keeps raising its take-profit target chasing an enormous multiple that a post-pump entry will never reach, and the position rides the reversal back down. The symptom the operator sees is "the bot became too strict and now it just chases pumps and dumps." The two complaints, too strict and trapped chasing, are not two problems. They are one.

The correct response, learned through this cycle several times, is counterintuitive: do not make the bot stricter. Keep the pool-score filter moderate so the bot catches tokens earlier in their curve rather than only at the peak. Keep the pool-size floor reasonable so the bot is not restricted to established, post-pump pools. Escalate the take-profit target only on genuine sustained momentum, not on noise, and cap the escalation so it captures real mega-runners without chasing a fantasy top. And above all, when the bot misbehaves, change one setting, watch a full session, and only then consider changing another. The endless oscillation between too-strict and too-loose is caused by changing five things at once and never letting any single change reveal its effect.

This failure mode has been documented in the project's own memory precisely so that it does not have to be rediscovered every time. It is the single most valuable piece of operating knowledge the project holds.

Part Eight: The Second Failure Mode, When Confidence Is Not Information

The strictness oscillation described above is a failure of the operator. Version 1.15.0 was written because of a failure of the machine, and it is a subtler and more interesting one.

Recall from Part Five that the learning agent is allowed to veto a buy, and that the veto is deliberately bounded: it only fully suppresses a purchase when the agent's bearish valuation exceeds its best buy valuation by a clear relative margin, roughly fifteen percent. The reasoning was sound. A half-trained network should not be able to switch off a strategy that is demonstrably making money, so the gate only closes on strong conviction.

On the fifth of August 2026 the agent returned the same bearish action, sell a portion of the position, for twenty-five consecutive pools. Its optimal action value sat at approximately 26.5 against a best-buy value of approximately 13.5, every single time. The margin test passed on every pool, so every buy was blocked. The bot stopped trading.

The guard was working exactly as written. That is the point. A policy that has collapsed onto a single action, that returns effectively the same valuation no matter what you show it, produces a large and perfectly stable gap between its favoured action and the alternatives on every input. A margin test is a test of magnitude, and a constant function satisfies a magnitude test trivially. The guard could not tell the difference between an agent that was extremely confident about these particular twenty-five pools and an agent that had stopped looking at pools altogether, because on the magnitude axis those two states are identical.

This is worth stating in its general form, because it is not a fact about this codebase. Magnitude cannot distinguish conviction from collapse. Only dispersion can. An agent that is genuinely evaluating its inputs produces valuations that vary with those inputs; an agent that has collapsed produces valuations that do not. The variance across inputs is the signal, and no amount of examining the magnitude of a single output will recover it.

The consequence for design is direct: any guard that reads a model's confidence in order to decide whether to act on it must also read whether that confidence is responsive to the input. Otherwise the guard is strongest precisely when the model is worthless, which is the worst possible failure ordering.
