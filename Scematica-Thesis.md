Scematica: A Complete Thesis From Conception to a Validated, Self-Aware Trading Organism

Version 1.15.0

Preface

This is the full story of Scematica, told in plain language and in order. It covers what the system is, why each piece exists, how the pieces fit together, and what the real data says about whether it works. It is written as an article, not a manual, so that a reader who has never seen the code can understand both the engineering and the reasoning behind it. Where numbers appear, they come from the project's own live trade log, not from marketing. The intent is that after reading this, you understand Scematica the way its builders do.

Part One: What Scematica Is

At its simplest, Scematica is a Solana trading bot. But that description undersells it. Scematica is really three cooperating machines wrapped in one code base. The first is a new-pool sniper that watches the Solana blockchain for the exact moment a new token becomes tradable on Raydium and, in the first few seconds of that pool's life, decides whether to buy, how much to buy, and when to sell. The second is a cross-decentralized-exchange arbitrage engine that looks for price differences between liquidity pools and captures them atomically. The third is a set of intelligence layers, most notably a pure-Rust deep reinforcement-learning agent, that watch the bot trade and learn to size and gate its decisions better over time.

Around those three machines sits a substantial amount of supporting infrastructure: a terminal dashboard, a web dashboard, an Android mobile app, an HTTP payment protocol implementation, a peer-to-peer agent marketplace, and a cryptographic settlement layer. None of that infrastructure exists for its own sake. Each piece was added to solve a concrete problem that appeared as the bot matured. The rest of this article walks through how that happened.

Part Two: Conception and the First Principle

Scematica began from a single observation about Solana memecoin trading. When a new token launches and its liquidity pool is created on a decentralized exchange, there is a very short window, often only seconds, in which the price behavior is most exploitable. Being early is everything. A human cannot react in that window. A bot can, but only if it is watching the right event stream, can evaluate a token's safety and quality almost instantly, and can submit a transaction with the right priority fee before the crowd.

That observation set the first principle that governs the entire code base to this day: speed and selectivity are in tension, and the money lives in resolving that tension correctly. If the bot is too slow, it arrives after the move. If it is too selective, it filters out everything and never trades, or worse, it only lets through tokens that are already at their peak. Almost every design decision in Scematica is, at bottom, an attempt to sit at the right point on that trade-off.

The project was built in Rust for reasons that follow directly from the first principle. Rust gives predictable, low-latency execution without a garbage collector pausing the program at the wrong microsecond, and it produces a single native binary that can be deployed close to a fast RPC node. The whole system targets Solana mainnet and is gated behind a token: to run the bot you must hold 250,000 of the project's own SCEMA token. That gate is both an access-control mechanism and an alignment mechanism, tying the people who use the tool to the token that represents it.

Part Three: The Sniper Pipeline, Stage by Stage

The sniper is the heart of Scematica, and it is best understood as a pipeline that a candidate token flows through.

The first stage is the listener layer. Several sources of new-pool events, a Raydium AMM V4 listener, a Pump.fun source, and a whale-copy source, all merge into a single unified event stream. Everything downstream is deliberately blind to where an event came from, which means new sources can be added without touching the rest of the pipeline. This is a recurring architectural theme in Scematica: define one clean seam, then let many implementations plug into it.

The second stage is the filter pipeline. Each filter is a small, independent unit that answers one yes-or-no question about a candidate pool: Is the mint authority renounced? Is the liquidity provider token burned? Is the pool large enough, but not so large it is already an established, post-pump token? Does the deployer have a history of rug pulls? Does the pool pass a predictive quality score? Filters run with a hard per-call timeout, three seconds, and they are designed to fail open rather than stall the whole queue when a single RPC node is slow. This matters enormously in practice, because the alternative, a pipeline that freezes when one network call hangs, forfeits the speed that is the entire point.

The third stage is the executor. Once a token passes the filters, the executor builds the actual swap transaction. It handles the lifecycle of the wrapped-SOL associated token account, constructs the Raydium swap instruction, and escalates the priority fee dynamically so the transaction lands even when the network is congested. Getting this layer right is the difference between a bot that decides to buy and a bot that actually buys.

The fourth stage is the sniper main loop, which orchestrates the whole thing: buy, then monitor the position, then exit. The sell monitor deserves special attention because it is where a great deal of the profit and pain lives. It runs in two phases. For the first twenty checks it polls the price every hundred milliseconds, watching for a rapid post-buy dump; a detector that fires on three consecutive declines catches the tokens that pump for a heartbeat and then collapse. After that initial burst it settles into a slower cadence. Crucially, it re-reads its take-profit and stop-loss parameters on every single iteration, which is what allows the operator to change strategy live, from the dashboard or the mobile app, without restarting anything.

A subtle but important design choice runs through all of this: configuration uses defaulted fields everywhere, so that adding a new setting never breaks an existing configuration file. The bot has evolved through many versions and dozens of new parameters, and an operator's old config keeps loading the whole way through.

Part Four: The Risk Subsystems

A trading bot without brakes is a way to lose money quickly. Scematica has a family of independent circuit breakers, each living in its own module, each able to pause buying on its own, and each following the same pattern so new ones can be added consistently.

There is an all-time-high tracker that pauses buying when the wallet draws down a configured percentage below its session high, so a good run cannot fully unwind. There is a grief breaker that watches cumulative loss inside a five-minute sliding window and halts if losses come too fast, which protects against a bad market regime or a spate of rugs. There is a fractional-Kelly position sizer that adjusts entry size from a rolling win rate, betting more when the edge is present and less when it is not. There is a pool scorer that turns a pool's age and liquidity into a predictive quality number and rejects anything below a threshold. There is a deployer-reputation ledger that blends each deployer's rug history into a moving average and rejects serial ruggers. And there is a multi-RPC failover that ranks endpoints by latency and rotates across them, because in this game a slow node is a lost opportunity.

The philosophy behind all of these is defensive asymmetry. The bot is designed to lose small and often, and to win big and rarely. The breakers exist to guarantee the "small" in "lose small." As the data will show, this asymmetry is not incidental. It is the entire source of profitability.

Part Five: The Deep Q-Star Agent

The most ambitious intelligence layer in Scematica is a reinforcement-learning agent written from scratch in pure Rust, with no external machine-learning framework. This was a deliberate choice: the agent lives inside the sniper process, must be fast, and must not drag in a heavy dependency tree. Everything, the neural network, the training loop, the replay memory, is hand-built.

The agent is a Double, Dueling Deep Q-Network. Its input is a twenty-four-dimensional description of the current trading situation, normalized to a common range: the pool's age and liquidity, recent price change and volume, the buy-to-sell ratio, whether liquidity is burned and mint authority renounced, the current profit-and-loss and position age, daily profit, win and loss streaks, wallet balance, market regime, volatility, spread, time of day, the number of open positions, and several velocity and acceleration signals that capture the shape of the price move. From that state the agent chooses among five actions: hold, buy at standard size, buy aggressively, sell part of the position, or sell all of it.

The training machinery is genuinely sophisticated for a hand-rolled implementation. It uses Double Q-learning, where one network selects the best action and a separate target network evaluates it, which reduces the well-known tendency of Q-learning to overestimate. It uses prioritized experience replay backed by a sum-tree, so the agent learns more from surprising transitions than from routine ones. It uses multi-step returns to propagate reward faster. It branches into separate network pairs per market regime once it has trained enough, so that "what to do in a bull regime" and "what to do in a panic regime" are learned separately. And it runs a small tournament of three parameter variants in parallel, promoting whichever is performing best.

The way the agent influences live trading is careful and conservative, and this care is itself a lesson. The agent does not get to trade freely from day one. It must first accumulate enough training steps and produce a signal with enough confidence. Only then does it begin to size entries, buying larger when it is bullish and smaller when it is unsure, and to veto a buy when it is strongly bearish. Even the veto is bounded: a weak bearish lean only downgrades the position size, and only a strong bearish signal fully suppresses a buy. This design exists precisely so that a half-trained network cannot silently switch off a proven, profitable strategy. It is a template for how to add a learning component to a system that already makes money: let it advise, then let it size, and only let it veto once it has earned the right.

Later work extended the agent with optional, opt-in modules: a distributional value head that models the full distribution of returns rather than just the average, a Dreamer-style latent world model that learns to imagine future states, and an adversarial pool simulator that trains the agent against a synthetic environment designed to fool it. These are research-grade additions, gated behind feature flags, that push the agent toward robustness.

Part Six: The Evolution of the Exit Strategy

If there is one part of Scematica that has been revised more than any other, it is the exit logic, the question of when to sell. This is not surprising. Entering a memecoin is a single decision; exiting one is a running battle against a price that can 10x or evaporate in seconds. The history of the exit strategy is a history of hard-won lessons, and it is worth recounting because it shows the project learning from its own mistakes.

Early versions suffered from a stale-target bug that quietly killed the escalation logic: the take-profit target was not being refreshed correctly, so a position that should have been allowed to ride a runner instead exited early. There was a velocity-window bug that mis-measured how fast the price was moving. There was a period where profit-and-loss was computed from an estimate rather than the actual swap output, which made the exit decisions subtly wrong. There was even a spectacular class of bug where a position would report a 99-percent profit that did not exist, traced back to how the momentum window re-armed at the 100-percent mark.

Each of these was found by staring at the real trade log, forming a hypothesis, and fixing the specific mechanism. Out of that process came the current exit architecture: a tiered partial-take-profit ladder that sells a slice of the position at each of several gain levels and, after the first tier fires, moves the stop to break-even so the trade can no longer become a loss; a profit-lock that permanently raises the stop toward break-even after the position holds above entry for several consecutive checks; a momentum escalator that raises the take-profit target as long as genuine velocity persists, so a real runner is allowed to run; a velocity-decay exit that bails when the price stops advancing; and a peak-stagnation exit that closes a position that has escalated but then stalled.

There is a mathematical invariant buried in this logic that the project had to learn the hard way, and it is worth stating because it captures the flavor of the whole exit problem: the peak that arms the pullback exit must exceed the sum of the initial take-profit and the pullback percentage, or the exit condition can never be satisfied and the position rides all the way down. Getting these thresholds to be mutually consistent, rather than each individually reasonable but collectively unsatisfiable, is most of the art.

Part Seven: The Recurring Failure Mode

Any honest thesis about Scematica must describe its most persistent failure, because understanding it is the key to operating the bot well.

Repeatedly, across many sessions, the bot has been broken in the same way. Someone, reacting to a run of losses, makes the filters stricter, demanding only the highest-quality, highest-scoring pools. The intuition is obvious: buy only the best. But the result is perverse. Because the sniper structurally arrives after a token's initial pump, the only pools that can pass a very high quality bar at the moment of detection are the ones that are still visibly ripping upward, which is to say the ones that are already parabolic and about to reverse. The bot buys the top. Then the momentum escalator, seeing a fast-moving price, keeps raising its take-profit target chasing an enormous multiple that a post-pump entry will never reach, and the position rides the reversal back down. The symptom the operator sees is "the bot became too strict and now it just chases pumps and dumps." The two complaints, too strict and trapped chasing, are not two problems. They are one.

The correct response, learned through this cycle several times, is counterintuitive: do not make the bot stricter. Keep the pool-score filter moderate so the bot catches tokens earlier in their curve rather than only at the peak. Keep the pool-size floor reasonable so the bot is not restricted to established, post-pump pools. Escalate the take-profit target only on genuine sustained momentum, not on noise, and cap the escalation so it captures real mega-runners without chasing a fantasy top. And above all, when the bot misbehaves, change one setting, watch a full session, and only then consider changing another. The endless oscillation between too-strict and too-loose is caused by changing five things at once and never letting any single change reveal its effect.

This failure mode has been documented in the project's own memory precisely so that it does not have to be rediscovered every time. It is the single most valuable piece of operating knowledge the project holds.

Part Eight: The Second Failure Mode, When Confidence Is Not Information

The strictness oscillation described above is a failure of the operator. Version 1.15.0 was written because of a failure of the machine, and it is a subtler and more interesting one.

Recall from Part Five that the learning agent is allowed to veto a buy, and that the veto is deliberately bounded: it only fully suppresses a purchase when the agent's bearish valuation exceeds its best buy valuation by a clear relative margin, roughly fifteen percent. The reasoning was sound. A half-trained network should not be able to switch off a strategy that is demonstrably making money, so the gate only closes on strong conviction.

On the fifth of August 2026 the agent returned the same bearish action, sell a portion of the position, for twenty-five consecutive pools. Its optimal action value sat at approximately 26.5 against a best-buy value of approximately 13.5, every single time. The margin test passed on every pool, so every buy was blocked. The bot stopped trading.

The guard was working exactly as written. That is the point. A policy that has collapsed onto a single action, that returns effectively the same valuation no matter what you show it, produces a large and perfectly stable gap between its favoured action and the alternatives on every input. A margin test is a test of magnitude, and a constant function satisfies a magnitude test trivially. The guard could not tell the difference between an agent that was extremely confident about these particular twenty-five pools and an agent that had stopped looking at pools altogether, because on the magnitude axis those two states are identical.

This is worth stating in its general form, because it is not a fact about this codebase. Magnitude cannot distinguish conviction from collapse. Only dispersion can. An agent that is genuinely evaluating its inputs produces valuations that vary with those inputs; an agent that has collapsed produces valuations that do not. The variance across inputs is the signal, and no amount of examining the magnitude of a single output will recover it.

The consequence for design is direct: any guard that reads a model's confidence in order to decide whether to act on it must also read whether that confidence is responsive to the input. Otherwise the guard is strongest precisely when the model is worthless, which is the worst possible failure ordering.

Part Nine: The Equations, and a System That Can Check Its Own Reporting

The fix for the collapse was not a better threshold. A better threshold would have been another magnitude test with a different number in it, and would have failed the same way at a different time. What the system needed was a quantity that goes to zero when the agent stops discriminating, and an instrument that reads it continuously.

That quantity is the intelligence ratio. Take the agent's optimal action value across the pools it has recently evaluated, compute the variance of those values, and divide by the square of their mean. The result is a dimensionless number, the squared coefficient of variation, that measures how much the agent's valuations depend on what it is being shown. A model returning the same value for every input has zero variance and therefore an intelligence ratio of zero, no matter how large or how confident that value is. Magnitude is not information, and this ratio is the arithmetic statement of that sentence. Scematica computes it over a rolling thirty-two-sample window, and treats anything below one ten-thousandth, roughly a one percent relative spread, as a policy that is no longer looking at its inputs.

The intelligence ratio is one of a small set of relations that version 1.15.0 turns from description into running instrumentation. They are documented separately, the statements in one file and the derivations in another, and it is important to be precise about their status. They are definitional, not derived from first principles. They do not forecast returns and they say nothing about the market. What they do is assign exact meaning to quantities the system already measures, and then, crucially, over-determine one of them.

That over-determination is where the value is. Agent capability is defined once as a product of expected return, exploration rate, and accumulated experience. It is defined a second time, implicitly, through a value identity relating it to the intelligence ratio and the normalised optimal value. Two definitions of the same quantity are not independent, and eliminating between them predicts the intelligence ratio from the other measurables. But the intelligence ratio is also defined independently as a measured variance. The system is consistent only where the predicted and measured values agree, and the difference between them, the residual, is a number the running bot can compute about itself.

Applied to the collapse, the residual localises the fault and gives it a sign. Measured dispersion went to zero; the predicted value, built from a positive exploration rate and two-odd normalised episodes, stayed strictly positive; so the residual went strictly negative. A negative residual has one meaning: the agent is holding high value while carrying no information. That is not a threshold anybody tuned. It falls out of the algebra, and it points at the exact component that had failed.

The same conclusion arrives by a second and completely independent route, which is the strongest evidence that the framework is describing something real. Optimal exploration, derived by maximising immediate expected value against the edge equation, turns out not to be a schedule at all but a ratio: it is set by how much the policy beats random action. As a policy collapses, the advantage it holds over random action goes to zero, and the optimal exploration rate diverges. The formal statement is that a non-discriminating agent should be exploring, not acting. Two derivations that share no intermediate steps both say the agent should have been off the gate. That agreement is why the framework earns the word instrument rather than the word decoration.

What was actually built from this is deliberately modest, and the modesty follows the same restraint that governs the agent itself. The sniper now carries an equation monitor alongside the agent. Past a sustained veto streak, the veto degrades from a hard gate to a size-down. A non-discriminating network keeps training, keeps its influence over position sizing, and can no longer silently kill the edge by holding the gate shut. The equation terms publish next to the agent's own snapshot, so a collapsed policy is visible on the dashboard rather than buried in a log file that nobody reads until the bot has been idle for a day.

Three further consequences fall out of the same algebra, and each of them sharpens something the project had previously known only as a scar.

The first concerns ordering. The edge equation carries a capture coefficient, the fraction of available edge the executor actually realises, as a multiplier in front of everything else. Selection quality and execution quality multiply; they do not add. An RPC layer that times out on one buy in two caps the whole system at half its potential no matter how good selection becomes. This is the algebraic reason infrastructure repair must precede selection tuning, and it means the ordering is forced rather than preferred.

The second is a precise restatement of the strictness lesson from Part Seven. Total edge is the acceptance rate multiplied by the expected profit of what gets admitted. Admitting in descending score order makes the second term non-increasing as the first grows, so their product has an interior maximum, and that maximum sits exactly where the marginal admitted candidate has zero expected profit. Admit above that line and edge is left unclaimed; admit below it and fees are paid to lose money. The sharp corollary is the one that would have prevented years of oscillation: a population whose average admitted profit is strongly positive is under-admitting, not performing well. The statistic every operator instinctively wants to maximise is the statistic that tells you the filters are too tight.

The third makes the payoff asymmetry unavoidable rather than merely observed. From a thirty-one percent win rate and a payoff ratio of fourteen and a half, the Kelly bound comes out at twenty-six percent of bankroll per position. The edge survives such a low hit rate only because of the payoff ratio, which is to say that any change compressing the right tail destroys the edge even if it raises the win rate. That is the quantitative form of the standing warning against curtailing the momentum escalation ladder during a losing stretch, and it converts an argument that used to be settled by intuition into one settled by arithmetic.

Two honesty constraints belong with all of this. The relations are definitional, so none of the constants is a prediction; they are historical summaries under configurations that have since changed. And a residual of zero means the components agree with one another, not that they are right. The instrument checks the system's reporting against itself. It cannot check the system against the world.

Version 1.15.0 carried one further piece of housekeeping that is worth a sentence because it is the same instinct applied to the build. The neural-network crate had drifted ahead of the rest of the stack, taken changes after its number was already published, and left the documented version table disagreeing with the manifests. Every crate now inherits a single workspace version. A component cannot drift ahead of the stack again without editing one line that moves all of them. It is a small thing next to the equations, but it comes from the same place: make the inconsistency impossible to express rather than relying on somebody noticing it.

Part Ten: The Arbitrage Engine

The second trading machine in Scematica is a cross-exchange arbitrage engine. Where the sniper is a directional bet on a new token going up, arbitrage is a market-neutral capture of price differences between liquidity pools. If the same token pair is priced differently on two exchanges, or if a cycle of three pools produces a round trip that ends with more of the starting token than it began with, there is a risk-free profit to be taken, minus fees.

The arb engine builds a graph of pools, searches it for profitable cycles, sizes the best one, and executes it. For most of its life the execution relied on a custom on-chain program whose only job was to enforce a profit-or-revert guarantee: if the round trip did not end profitably, the whole transaction would revert. Deploying that program to mainnet costs real SOL, and the project eventually recognized that the program was unnecessary. Solana transactions are atomic; if any instruction in a transaction fails, the entire transaction is undone. So the same profit-or-revert guarantee can be obtained for free by composing the swaps into a single transaction and setting the minimum output on the final hop to the starting amount plus the required profit. If the arbitrage does not clear that bar, the final swap fails, the whole transaction reverts, and the only cost is the network fee. This is how most professional arbitrage bots operate, and Scematica now runs program-less by default, meaning it can be started with no on-chain deployment at all.

The arb engine draws its pool graph from a seeded set of pool definitions fetched from the exchanges' public interfaces. Keeping that seed current is an operational task, and the tooling to refresh it is part of the project.

Part Eleven: ScemaDEX and the Agentic Liquidity Layer

Beyond the two trading machines sits the most conceptually adventurous part of the project: ScemaDEX, an agentic liquidity layer that reframes the whole idea of a decentralized exchange. The premise is that the routing intelligence itself, the decision about how to execute a swap, is a product that can be metered, sold, and improved, rather than a fixed piece of infrastructure.

ScemaDEX is organized around a set of primitives that build on one another. The first is metered inference routing: every quote is produced by a learning policy, and the quality of that decision can be sold per call over an HTTP payment rail. The second is intent solving: a caller expresses what they want, a swap objective, rather than a precise path, and the policy decides the venue, the split, and the timing. The third is a signal and reputation oracle that turns reputation scores and pool assessments into paid, readable endpoints. The fourth, and the defining one, is Conviction Routing, in which the policy escrows a slashable performance bond against its own promise: meet the guarantee and reclaim the bond plus a fee; miss it and the bond settles to the caller. This is what makes a paid, black-box inference trustworthy, because the seller has real money at stake on being right.

On top of those, a further set of adversarial primitives were added, each without clear precedent. A counter-market lets any agent stake against an open bond, creating the first market that prices individual machine inferences and producing a brand-new signal, the gap between an agent's self-confidence and the market's implied confidence. A scar market turns the trajectory behind a slashed bond into sellable, verified negative training data, on the logic that a decision which cost real collateral is the only un-fakeable proof of a genuine mistake. An experience-royalty ledger records which purchased experience trained which policy and streams a slice of downstream fees back to the original sellers, making training data a yield-bearing asset. And bonded teaching lets a teacher answer a student's most uncertain questions for a fee, bonding its tuition against the student's measured improvement, which is distillation with a money-back guarantee.

Compose all of that across many nodes and the result is a marketplace where autonomous agents sell bonded inferences and learned experience to one another, an economy of machine intelligence rather than a swap widget. Whether or not that vision is fully realized, the primitives are implemented, tested, and shipped as a real software development kit.

Part Twelve: The Payment Rail and the Settlement Machine

Underneath ScemaDEX's economics is a payment protocol. Scematica includes a Rust-native implementation of the HTTP 402 Payment Required standard, the mechanism by which a server can demand payment for a request and a client can satisfy it. This is what makes "sell an inference per call" a concrete transaction rather than an idea.

The most recent and most technically demanding addition to this layer is a settlement state machine with a dispute window. In its original form, a bond settled instantly and unchallengeably: the moment a fill came back, the system decided honored or slashed and that was final. The settlement redesign turns this into an optimistic lifecycle. A bond moves from escrowed to provisional for the length of a dispute window, during which it can be challenged; a challenge moves it to disputed; and only then is it finalized as honored or slashed. A configuration that sets the dispute window to zero collapses the whole thing back to the original instant behavior, which means the new machine is a strict superset of the old one and nothing that worked before is broken.

Two further ideas round out the settlement layer. The promise that a bond guarantees was abstracted behind a general interface, so that the same settlement machinery can enforce not only swap fills but arbitrary claims, and a non-swap forecast bond was implemented to prove the point. And a new insurance-and-reinsurance primitive was added, where a pool underwrites bonds and prices its premiums off the reputation of the party being insured, so that fresh, unproven identities pay full rate while established ones earn a discount.

The final piece is a genuine cryptographic proof of inference. The problem it solves is that a dispute window has to be long only because refuting a bad inference is slow: a challenger must hold the model, re-run the entire computation, and catch the lie. Scematica implements two backends that shrink that window. The first is a transparent, hash-based proof, the same soundness family as a zero-knowledge STARK, in which the prover commits to its entire execution trace and answers a handful of random challenges, and a verifier confirms the output is a correct forward pass by checking only those few spots, without re-running the network. The second is a real zero-knowledge SNARK backend built on the arkworks Groth16 system over the BN254 curve, in which the model's weights are baked into the proving and verifying keys as circuit constants, so the proof is a couple of hundred bytes, reveals nothing about the weights, and is verified without the model at all. Both plug into the same interface, so a deployment can swap proof systems without touching the settlement logic. This is advanced cryptography, implemented and tested, in service of a concrete goal: making it possible to trust a machine's claim about its own computation without redoing that computation.

Part Thirteen: The Interfaces

A trading system is only as good as an operator's ability to see and steer it. Scematica grew three interfaces over time.

The first is a terminal dashboard built with a Rust text-user-interface library. It shows live metrics, trades, the state of the learning agent, and a set of controls. It communicates with the sniper through a deliberately simple mechanism: not a socket or a message bus, but plain files in the working directory. The sniper writes its log, its metrics, its trade history, and its filter statistics to files; the dashboard tails them. The dashboard issues commands, pause buying, force-sell, change rate mode, by writing small JSON files that the sniper reads. Every writer uses a write-to-temporary-then-rename pattern so that a reader never sees a half-written file. This file-based approach is unglamorous and completely robust, and it is a good example of the project choosing the simplest thing that cannot break over the sophisticated thing that can.

The second is a web dashboard built with a modern JavaScript framework, backed by an HTTP API that serves the sniper's state files as JSON and accepts control commands. This exposes the same monitoring and control surface through a browser, with a real Solana wallet connection for the token gate.

The third, and newest, is an Android mobile application. It is important to be precise about what it is and is not. The sniper does not run on the phone; it cannot, because it needs a persistent low-latency connection to a fast node and would be killed by a phone's background limits, and putting a hot trading key on a phone would be reckless. Instead, the app is a companion remote. It wraps the web dashboard, and it pairs to the operator's own self-hosted bot over a token-gated connection, so that the operator can monitor and control their bot, including a full set of controls and finger-friendly sliders for take-profit, stop-loss, and size, from their phone, while keys and capital never leave their own machine. The app has a beginner mode that shows a clean, simplified view and a pro mode that exposes the full control set, so it serves both a newcomer and an expert. Connecting a wallet on the phone uses the standard mobile deep-link protocol to open a wallet app like Phantom for the membership check.

Building the mobile app produced its own set of hard-won lessons that are characteristic of real engineering. An early build crashed instantly on launch, traced to a push-notification library that bundled a component which demanded a configuration file that was not present. The build's size mysteriously grew every time until it was discovered that the finished app was being copied into a folder that the next build then bundled into itself, nesting the app inside itself and compounding its size. Each of these was diagnosed from the evidence and fixed at the root. The result is a small, signed, crash-free application.

Part Fourteen: What the Data Actually Says

None of the engineering matters if the bot does not make money. So the most important section of this thesis is the one grounded entirely in the real trade log.

Across 685 completed round-trip trades collected over a nine-and-a-half-day window, the bot returned a net realized profit of just over 2.26 SOL. It did this while winning only 28.9 percent of its trades. The reason a low win rate produces a strong profit is the payoff asymmetry: the average winning trade returned about 0.0135 SOL, while the average losing trade cost only about 0.00094 SOL, a ratio of more than fourteen to one. Expressed as a profit factor, the standard measure of how much a strategy makes for every unit it loses, the number is 6.50. For every 1 SOL Scematica lost over this window, it made back 6.50.

The profit is highly concentrated, which is exactly what one expects from a strategy built on rare large winners. The best ten percent of trades produced seventy-eight percent of the net profit. The single best thirty-three trades produced nearly half of it. This concentration is not a weakness; it is the signature of the edge. It also dictates the correct operating discipline: survive the many small losses cheaply, and never, under any circumstance, cut a winner short, because cutting winners short throws away the tail that is the entire source of profit.

The data is granular enough to be prescriptive. Sorted by entry size, positions below about 0.004 SOL are net negative, eaten by fees and spread, while the band from about 0.0075 to 0.015 SOL is the profit core, responsible for the majority of net gains. Sorted by hold time, the first five seconds after entry contain the majority of the profit, confirming that speed is paramount, while a dead zone from about forty-five to one-hundred-twenty seconds wins only seven percent of the time and exists to be exited quickly, and the rare position held beyond several minutes wins seventy-five percent of the time because it is a genuine runner. Sorted by hour, only two hours of the day are net negative, and the single most profitable hour is one that an earlier misguided configuration had actually blocked. Sorted by weekday, Monday and Tuesday together produce almost all of the profit, and Sunday is the only losing day, which is precisely why a defensive weekend mode exists.

From the same log the capital requirement can be computed rather than guessed. The bot never held more than about 0.099 SOL in open positions at once, and its worst peak-to-trough equity dip was about 0.164 SOL. From those two facts, a minimum viable trading bankroll of half a SOL, a recommended bankroll of seven-tenths to one SOL, and a comfortable scaling bankroll of two to three SOL follow directly. Because position sizing is a percentage of the wallet, the edge compounds automatically as the balance grows, so scaling is a matter of funding the wallet and proving that live slippage does not erode the historical edge, rather than re-tuning the strategy.

A narrower slice of the same log, the 639 positions that had closed when the version 1.15.0 constants were measured, decomposes cleanly enough to check the arithmetic against itself. Win rate 30.99 percent, average win 0.013512 SOL, average loss 0.000934 SOL, payoff ratio 14.46, profit factor 6.49. Expectancy computed from those components comes to 0.003542 SOL per closed position, and net profit divided by position count comes to the same figure to six decimal places. That agreement is not a result, it is a validation of the decomposition, and it is the reason the Kelly bound derived from these numbers in Part Nine can be taken seriously rather than treated as a plausible-looking quotient.

There is one caveat that intellectual honesty requires. This is a realized result over a particular historical window, not a guarantee of future performance. No trading system can promise the future, and the two variables a historical log cannot fully capture, live slippage on larger entries and competition from other bots, are exactly the ones that matter most when scaling. The honest claim, and it is a strong one, is that Scematica has a real, repeatable, statistically significant edge that showed up clearly over hundreds of trades. The way to realize that edge going forward is discipline, not new features.

Part Fifteen: The Philosophy That Ties It Together

Step back from the individual pieces and a consistent philosophy emerges, and it is worth naming because it explains why the project looks the way it does.

The first thread is asymmetry. Everything, the risk breakers, the exit ladder, the position sizing, the whole shape of the returns, is built around losing small and often while winning big and rarely. The bot is not trying to be right; it is trying to be paid.

The second thread is clean seams. Listeners merge into one event stream. Filters share one interface. Risk breakers share one pattern. Proof systems share one role. The learning agent advises through a bounded channel. Time after time the project defines a single narrow contract and then lets many implementations plug into it, which is what has allowed it to grow so much surface area without collapsing under its own weight.

The third thread is honesty with the data. Nearly every fix in the project's history came from staring at the real trade log, forming a specific hypothesis about a specific mechanism, and correcting that mechanism. The bot's own history of loss reports, its 99 percent phantom-profit bug, its strict-then-trapped oscillation, was documented and learned from rather than hidden. Even this thesis is grounded in the log rather than in optimism.

The fourth thread is restraint about power. The most dangerous component, the learning agent, is the most carefully leashed. The most expensive component, the on-chain arb program, was recognized as unnecessary and removed. The riskiest claim, guaranteed profit, is one the project refuses to make even when it would be flattering. Power is added cautiously and only after it earns trust.

The fifth thread is the newest, and version 1.15.0 is where it became explicit: turn scars into instruments. For most of its life this project learned by losing money, forming a hypothesis, fixing a mechanism, and writing the lesson down so it would not have to be relearned. That works, but it scales badly, because every lesson lives in a document that somebody has to remember to read. The equations are an attempt to do better, by taking the things the project already knew and giving them a form the running system can evaluate about itself. The warning against over-tightening the filters becomes a condition on the marginal candidate. The warning against cutting winners becomes a Kelly bound that shows the payoff ratio, not the hit rate, carrying the strategy. The instruction to fix the RPC path before tuning selection becomes a multiplication rather than an addition. And the failure that nobody had anticipated, an agent confidently valuing pools it had stopped looking at, becomes a variance that goes to zero and a residual whose sign names the broken component. A lesson written in prose has to be remembered. A lesson written as a measured invariant announces itself.

It is worth being honest about the limits of that fifth thread, because overselling it would betray the third. The relations are definitional, not physical. They do not predict the market, and a residual of zero means only that the system's components agree with each other. What the instrument catches is the system lying to itself, which turns out to be a large enough category of failure to be worth catching.

Conclusion

Scematica started as a simple idea, that being first to a new Solana token is worth money if you can act in the first few seconds safely, and grew into a layered system that is part trading bot, part reinforcement-learning experiment, part cryptographic marketplace, and part cross-platform product. Along the way it accumulated real scars: bugs that lost money, configurations that broke it, an agent that stopped looking at its inputs while sounding more certain than ever, a mobile app that crashed and then bloated, each fixed at the root and remembered so it would not recur.

Version 1.15.0 is the point at which the project stopped only remembering and started measuring. The system now computes a small number of quantities about its own behaviour and can tell when its own components have stopped agreeing with one another. That is a modest capability described precisely, and it is deliberately described that way: it detects the machine deceiving itself, not the market surprising it. But the class of failure it covers is the one that had just cost the bot a day of trading while every log line read as healthy, and the guard that missed it was a guard written in good faith by someone who understood the system well. That is the case for instrumentation over vigilance.

What remains is a system with a genuine, data-proven edge, a profit factor of 6.50 over hundreds of live trades, and a clear-eyed understanding of exactly how to run it: the right capital, the right entry size, the right hours, a fast connection, moderate filters that catch tokens early, and the discipline to take small losses without flinching and let the rare large winner run. The engineering is ambitious and the cryptography is real, but the lesson at the center is simple and old. Find an asymmetric edge, protect it from your own worst instincts, and let it compound. What version 1.15.0 adds is the observation that your own worst instincts now include those of the machine you built to help you, and that it too should be asked to show its work.
